# 사내 AI 챗봇 운영 효율 대시보드 발표 준비 가이드

## 1. 발표 핵심 메시지

> 이 프로젝트는 챗봇 사용량을 자랑하는 대시보드가 아니라, 실제 해결 여부를 측정하고 문제를 찾아 개선한 뒤 다시 측정하는 운영 시스템입니다.

발표 내내 아래 세 가지를 유지합니다.

1. 사용량 증가만으로 성공이라고 판단하지 않았습니다.
2. 해결률, 재질문, 동료 재문의, 답변 경로, Token, 오류를 함께 분석했습니다.
3. 3개월 성과는 완성이 아니라 개선 가능성을 확인한 결과입니다.

## 2. 발표 전 준비

- 터미널에서 프로젝트 폴더로 이동합니다.
- 가상환경을 활성화하고 `pip install -r requirements.txt`를 실행합니다.
- `streamlit run app.py`로 대시보드를 실행합니다.
- 브라우저 배율은 80~90%로 맞춥니다.
- 사이드바 기간은 `전체`, 질문 분야는 `전체`로 둡니다.
- 발표 직전 1~6번 탭이 정상적으로 열리는지 확인합니다.
- 실시간 화면을 보여줄 경우 별도 터미널에서 `python scripts/hourly_monitor.py`를 실행합니다.
- 알림 데이터가 없더라도 장애가 아닙니다. “현재 새 이상 신호가 없다”는 운영 상태입니다.
- 모든 수치는 프로젝트용 시뮬레이션 데이터임을 처음에 밝힙니다.

이 문서는 발표자만 확인하는 자료입니다. `왜 이 프로젝트를 만들었는가`, 발표 시간 배분, 발표 멘트와 같은 진행 안내는 대시보드 화면에 표시하지 않습니다.

## 3. 5분 발표 순서

### 0:00~0:40 — 문제 제기

7번 `개선 Action`의 3단계 비교표를 보여줍니다.

발표 멘트:

> 사내 챗봇을 도입해도 질문 수만 보면 실제 도움이 되었는지 알 수 없습니다. 도입 전 월 250건의 동료·지원부서 문의 과정과 챗봇 도입 초기, 3개월차를 나누어 비교했습니다.

### 0:40~1:30 — 무엇을 측정했는가

3단계 비교표 아래의 도입 전 시간 지표를 보여줍니다.

발표 멘트:

> 도입 전에는 자료 검색 6.7분, 질문 작성 2.0분, 지원부서 답변 대기 41.8분이 필요했고, 지원부서에는 문의 1건당 9.3분의 실제 답변 작업이 발생했습니다. 도입 후에는 사용자가 직접 확인한 챗봇 해결률과 재질문을 중심으로 품질을 측정했습니다.

도입 전 해결률은 사람에게 문의한 결과이고, 도입 후 해결률은 챗봇 자체 해결 결과입니다. 두 값을 같은 성능 지표처럼 직접 비교하지 말고, 문의 경로가 달라진 전후 상황으로 설명합니다.

### 1:30~2:30 — 개선 방식

`적용 결과` 카드와 개선 액션 표를 보여줍니다. 표의 모든 행을 읽지 말고 세 가지만 설명합니다.

- 반복 질문을 FAQ로 등록해 불필요한 LLM 호출을 줄였습니다.
- 해결률이 낮은 Mac VPN 문서를 보완해 RAG 품질을 개선했습니다.
- 관련 없는 문서 Chunk를 줄여 요청당 Token을 낮췄습니다.

발표 멘트:

> 대시보드에서 문제를 발견한 뒤 로그와 답변 경로로 원인을 좁히고, 조치를 적용한 뒤 같은 지표로 다시 측정했습니다.

### 2:30~3:30 — 결과

`운영 성과` 카드를 보여줍니다.

발표 멘트:

> 초기 1개월의 해결률은 30.0%였고 3개월차에는 45.1%로 15.1%p 상승했습니다. 재질문과 동료 재문의도 감소했습니다. 다만 해결률이 아직 절반에 못 미치기 때문에 완성된 서비스라고 과장하지 않고, 개선 방향성이 확인된 단계로 해석했습니다.

### 3:30~4:20 — 실제 운영 화면

1번 `운영 요약`으로 이동한 뒤 3번 `질문 품질`을 짧게 보여줍니다.

발표 멘트:

> 운영자는 첫 화면에서 현재 해결률과 위험 신호를 확인합니다. 다음으로 질문 품질 탭에서 해결률이 낮고 재질문이 많은 Topic을 찾아 지식 보완 순서를 정합니다. 상세 데이터는 필요할 때만 펼치도록 구성했습니다.

### 4:20~5:00 — 다음 단계와 결론

7번의 `다음 개선` 카드를 보여줍니다.

발표 멘트:

> 다음 목표는 미해결 질문을 줄이는 것입니다. 낮은 해결률 Topic의 문서를 보완하고 RAG 검색 범위와 오류 원인을 조정한 뒤 같은 KPI로 다시 측정하겠습니다. 이 대시보드는 성과를 과장하는 화면이 아니라, 실제 문제를 찾아 개선하는 운영 도구입니다.

## 4. 1~6번 운영 화면 설명법

| 화면 | 실무 질문 | 화면에서 할 일 |
|---|---|---|
| 1. 운영 요약 | 지금 상태가 좋은가? | 해결률과 위험 신호 확인 |
| 2. 도입 전후 비교 | 사람 문의 부담과 챗봇 품질이 어떻게 달라졌나? | 도입 전·초기·3개월차 3단계 확인 |
| 3. 질문 품질 | 무엇부터 고쳐야 하나? | 해결률 낮고 재질문 높은 Topic 선택 |
| 4. 답변 경로 | 어떤 방식으로 답했나? | FAQ·RAG·LLM 역할과 효율 비교 |
| 5. 비용 효율 | 자원을 낭비하고 있나? | Token/해결건과 상위 사용 원인 확인 |
| 6. 시스템/오류 | 서비스 문제인가? | 오류·지연·자원 추이로 장애 원인 확인 |

## 5. 예상 질문과 답변

### 왜 사용량이 아니라 해결률이 핵심인가요?

사용량은 호기심이나 반복 질문 때문에 늘 수 있습니다. 사용자가 실제 해결되었다고 확인했는지와 다시 질문했는지를 함께 봐야 업무 효과를 판단할 수 있습니다.

### 45.1%면 성과가 낮은 것 아닌가요?

맞습니다. 완성 단계는 아닙니다. 다만 초기 30.0%에서 개선되었고, 어떤 Topic과 운영 요소를 고쳐야 하는지 측정 가능한 구조를 만들었다는 점이 프로젝트 성과입니다.

### 데이터는 실제 회사 데이터인가요?

아닙니다. 회사와 성과 데이터는 프로젝트용 시뮬레이션입니다. 따라서 절대적인 사업 성과가 아니라 측정·개선 구조를 시연하는 데 목적이 있습니다.

### Token이 많은 직원을 감시하는 화면인가요?

아닙니다. 개인의 과다사용으로 단정하지 않습니다. 요청량, 긴 Context, RAG 검색량, 재시도와 오류를 함께 확인해 시스템이나 지식 구조의 문제를 찾습니다.

### CPU와 메모리는 왜 보나요?

업무 성과 지표가 아니라 응답 지연이나 오류가 발생했을 때 원인을 확인하는 보조지표입니다.

### FAQ와 RAG의 차이는 무엇인가요?

FAQ는 반복되는 정형 질문을 미리 검토한 답변으로 처리합니다. RAG는 사내 문서에서 관련 부분을 찾아 LLM이 답변하도록 합니다.

## 6. 발표 시 주의할 표현

- “효율이 완전히 입증되었습니다” 대신 “개선 방향성을 확인했습니다”라고 말합니다.
- “직원이 Token을 과다 사용했습니다” 대신 “상위 사용의 원인을 확인합니다”라고 말합니다.
- “CPU가 높아서 업무 효율이 낮습니다” 대신 “오류나 지연의 원인 후보로 확인합니다”라고 말합니다.
- 250건은 도입 전 월 문의 기준입니다. 챗봇 요청 600건·850건과 같은 의미로 비교하지 않습니다.

## 7. 비상 대비

- 화면이 멈추면 브라우저 새로고침 후 다시 7번 개선 Action으로 이동합니다.
- 포트 충돌 시 `streamlit run app.py --server.port 8502`로 실행합니다.
- 실시간 모니터가 비어 있으면 저장된 3개월 데이터 분석 부분만 시연합니다.
- 발표 전에 7번 개선 Action 전체 화면을 PDF나 화면 캡처로 별도 보관하면 안전합니다.
